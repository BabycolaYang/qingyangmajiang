# 技术架构

## 目标

第一阶段做手机端好友房青阳平胡麻将，支持欢乐豆结算。服务端必须是规则和结算的唯一权威，客户端只负责展示状态和提交玩家动作。

## 推荐选型

### 手机端

- React Native + Expo
- TypeScript
- 横屏牌桌优先，兼容常见 iPhone 和 Android 屏幕

原因：开发效率高，适合快速做大厅、好友房、牌桌、战绩、钱包等业务界面。

### 服务端

- NestJS
- Socket.IO
- TypeScript

原因：好友房天然适合 WebSocket 房间模型；Socket.IO rooms 可以承载房间广播、断线重连和观战扩展。

### 数据层

- PostgreSQL：用户、房间、牌局、战绩、欢乐豆流水。
- Prisma：类型安全的数据访问。
- Redis：在线状态、房间临时状态、Socket.IO 多实例适配。

### 共享规则包

- `packages/mahjong-core`
- 只放纯逻辑，不依赖 UI、数据库或网络。
- 服务端调用它做胡牌、跑风、计分和回放校验。
- 客户端可以调用它做提示，但客户端结果不能作为最终结算依据。

## 目录规划

```text
apps/
  mobile/   手机端 App
  server/   好友房、账户、牌局服务
packages/
  mahjong-core/   青阳平胡规则核心
docs/
  rules/    规则文档
```

## 服务端边界

服务端负责：

- 洗牌、发牌、摸牌。
- 骰子结果生成。
- 赖子翻牌。
- 碰、杠、胡动作校验。
- 跑风判定。
- 欢乐豆结算。
- 牌局日志和回放。
- 断线重连后的状态恢复。

客户端负责：

- 展示手牌、弃牌、碰杠区和玩家状态。
- 提交玩家动作意图。
- 播放动画和声音。
- 展示战绩、欢乐豆和房间邀请。

## 欢乐豆原则

- 1 分 = 1 欢乐豆。
- 每次结算必须生成流水。
- 流水必须幂等，避免断线重试导致重复扣豆。
- 欢乐豆只作为游戏内积分，不设计提现、现金兑换或高价值实物兑换。

## 后续里程碑

1. 规则核心：牌墙、回合、碰杠、胡牌、跑风、结算。
2. 牌局模拟器：机器人自动打牌，用于压力测试规则。
3. 好友房服务：创建房间、加入房间、准备、开局、解散。
4. 手机端牌桌：横屏布局、手牌交互、动作按钮。
5. 欢乐豆账户：余额、流水、每日赠送、牌局结算。
